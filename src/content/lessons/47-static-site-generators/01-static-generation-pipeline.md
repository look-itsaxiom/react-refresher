# Static generation as a data pipeline

Strip away the marketing and a static site generator (SSG) is one pipeline: **data
sources → templates → HTML and assets, written to disk once, at build time.** No server
runs to produce the response a browser gets; a request just retrieves a file a CDN
already has. That's the entire value proposition — the previous lessons in this track
covered CSR, SSR, and streaming, all of which do work *per request*. SSG does the work
once, offline, and amortizes it over every visitor.

## Content collections: typed data from files

Early SSGs (Jekyll, old Hugo) treated each Markdown file as an ad-hoc bag of frontmatter.
Astro's **content collections** (formalized further by the Content Layer API in Astro 5,
stable through Astro 7) made that bag typed: you declare a Zod schema per collection —
`title: z.string()`, `publishedAt: z.date()`, `tags: z.array(z.string())` — and the build
fails loudly if a Markdown file's frontmatter doesn't match, instead of shipping a page
with `undefined` where a date belongs. `astro:content`'s `getCollection()` and
`getEntry()` return fully-typed entries; your editor autocompletes `entry.data.tags`
because the schema *is* the type. Docusaurus and VitePress take a lighter version of the
same idea — sidebar and doc metadata still comes from frontmatter, just with less
validation machinery around it.

The **loader** is the part that decides where entries come from. A `glob()` loader reads
a directory of Markdown/MDX files. A `file()` loader reads one JSON/YAML file as a whole
collection. A custom loader can hit a CMS's REST API, a database, or a spreadsheet at
build time — the schema and the templates downstream don't care where the data
originated, only that it matches the shape they were promised. This is the same
separation of concerns you'd want in any data layer: fetch-and-validate is one job,
render is a different one.

## The Markdown/MDX pipeline

Turning Markdown text into HTML is itself a small pipeline, and this course's own lesson
renderer is a working example of it: Markdown source → **remark** (parses Markdown into
an AST, and runs plugins like `remark-gfm` for tables/strikethrough) → **rehype**
(operates on the resulting HTML AST, running plugins like `rehype-shiki` or this course's
own Shiki integration for syntax-highlighted code blocks) → HTML string or React tree.
`react-markdown` in this course's UI is exactly this: it parses your lesson's `.md` files
with remark, highlights fenced code with Shiki (the same highlighter VitePress and
Starlight use), and renders the result as React elements — no `dangerouslySetInnerHTML`
needed, because the AST is walked into real elements rather than serialized to an HTML
string and reparsed.

**MDX** (now MDX 3, and the format both Astro's and Next.js's content layers support)
extends this by letting a Markdown file `import` and render actual components inline —
`<Callout>` or `<CodeTabs>` alongside prose — compiled once at build time rather than
interpreted at request time. It's Markdown's readability plus a component's
interactivity, without a client-side Markdown parser shipped to the browser.

## Slugs, routing, pagination, and taxonomy

An SSG's router is usually just: **filename → URL.** `blog/hello-world.md` becomes
`/blog/hello-world/` unless frontmatter overrides the slug explicitly. That mapping has
to be deterministic and collision-free, which is why most generators kebab-case the
filename by default (spaces and underscores become hyphens, case is lowered) rather than
using the filename verbatim.

Two problems don't fall out of "one file, one page" automatically:

- **Pagination.** A blog index with 400 posts needs to become `/`, `/page/2`,
  `/page/3`, ... each rendering a slice of the sorted entries, with `prev`/`next` links
  computed from the total count and a page size.
- **Taxonomy pages.** `/tags/react/` needs to exist even though no file named
  `tags/react.md` does — it's generated by grouping entries by a frontmatter field and
  emitting one page per unique value.

Both are pure functions over the already-validated collection: given entries and a page
size, compute pages; given entries and a grouping key, compute one page per group. The
build script just needs to call `getStaticPaths` (Next.js/pages router),
`generateStaticParams` (Next.js App Router), or Astro's equivalent once per computed
path, and the framework emits one HTML file per invocation.

## Build-time everything else

Once the pipeline exists, everything else that used to require a running server gets
pulled into the same build step:

- **Images.** Astro's `<Image>` and Next.js's `next/image` (in static-export mode)
  resize, reformat (AVIF/WebP), and hash images *once*, at build time, rather than on
  every request — the opposite of an image CDN's per-request transform, and cheaper for
  content that doesn't change per visitor.
- **OG cards.** Generating a per-page social preview image (title + site branding
  rendered to PNG) at build time means zero runtime cost and a stable, cacheable URL per
  page.
- **Sitemaps and feeds.** `sitemap.xml` and an RSS/Atom feed are both just a fold over
  the same page list the router already computed — emit them once, alongside the HTML.
- **Search.** Client-side search over static content (Pagefind is the current standard,
  used by Astro Starlight and increasingly VitePress/Docusaurus sites) indexes the
  *built* HTML after the fact, shipping a small WASM-backed index the browser queries
  locally — no search server, because the corpus never changes between deploys.

## Why this is the cheapest thing to host

Every one of the above happens once per build, not once per request. The output is a
directory of files with content hashes in their names, which means **immutable caching**:
a CDN can cache `main.a3f9c1.js` forever, because a change to the file produces a
different name, and the HTML that references it is the only thing that needs revalidating
on deploy. There's no server process to keep warm, no database connection pool to size,
no per-request compute bill — the entire runtime cost of serving the site is "read a file
off disk (or edge cache) and send it." That's the ceiling every other rendering strategy
in this track is measured against, and the next concept step covers where that ceiling
stops being high enough.
