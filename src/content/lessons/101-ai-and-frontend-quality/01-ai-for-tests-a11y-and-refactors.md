## AI for tests, a11y, and refactors: what it's good at, and how to check it

An agent will happily write you fifty tests before lunch. The question this lesson is
about is not "can it write tests" — it's "how do you know the tests it wrote are worth
anything, without reading every line yourself." Lessons 98 and 99 covered the tools and
the prompting. This one is about the check: the mechanical, repeatable step that tells
you whether AI-generated tests, accessibility fixes, and refactors actually did what they
claim.

### Tests generated from the wrong thing

Ask an agent to "write tests for this component" and it has two possible sources of
truth: the spec (what the component is *supposed* to do) or the implementation (what the
code *currently* does). Generating from the implementation is the trap. If the component
has a bug — an off-by-one in pagination, a race condition in a debounced search — a test
generated by reading the code will assert the buggy behavior, pass immediately, and
enshrine the bug as "tested." You end up with green CI and a real defect at the same
time. Generating from the spec (a PR description, an issue, a docstring, or you dictating
the intended behavior) is slower but is the only version that can catch the bug it's
supposed to catch.

In practice this means: before you accept an agent's test file, ask "would this test
have failed on the code as it existed *before* the fix it's testing?" A test that only
passes against the final implementation and would have passed against a subtly wrong one
too isn't testing the behavior — it's testing that the code doesn't crash.

### Test smells an AI tends to produce

A handful of patterns show up disproportionately often in AI-generated test files,
because they're the path of least resistance to a passing test:

- **Tautological assertions** — `expect(true).toBe(true)`, or `expect(2).toBe(2)`. These
  pass by construction and test nothing.
- **No assertion at all** — a test that renders a component, maybe clicks a button, and
  never calls `expect`. It "passes" the way an empty function passes.
- **Snapshot overuse** — `toMatchSnapshot()` on every test, which turns "did this
  component keep working" into "did this component's serialized DOM change at all,"
  including changes that are completely fine.
- **Mocking the unit under test** — `vi.mock('./Cart')` inside `Cart.test.tsx`. Once the
  subject is mocked, every test is exercising the mock's return value, not the real
  component.
- **Testing implementation details** — `container.querySelector('.cart-item')` or
  `getByTestId('submit-btn')` where a role or text query (`getByRole('button', { name:
  /submit/i })`) would find the same element the way a user actually finds it. This isn't
  automatically wrong — Testing Library's own guide leaves `getByTestId` as an escape
  hatch — but reaching for it as the *first* choice is usually a sign the test was
  written by reading the JSX rather than by asking "what would a user do."
- **Missing negative cases** — every test in the file is the happy path; nothing checks
  an invalid input, an empty list, or an error response.

None of these are hard to produce with a prompt like "add tests for this file" and no
follow-up. They're also mechanically detectable — you'll build a scanner for exactly
these patterns in the next exercise.

### Mutation testing: the check that catches all of the above

Code coverage answers "did any test execute this line." It says nothing about whether a
test would notice if that line were wrong. Mutation testing answers the question
coverage can't: a tool (Stryker is the standard one for JavaScript and TypeScript, at
stryker-mutator.io) takes your source, applies a small, mechanical change — a *mutant* —
such as flipping `===` to `!==`, or `<` to `<=`, and reruns your test suite. If a test
fails, the mutant is **killed**. If every test still passes, the mutant **survived** —
your tests would not have noticed that exact bug. The **mutation score** is the
percentage of mutants killed. A test suite with 100% line coverage and a 40% mutation
score is a suite that runs every line and checks almost nothing about what those lines
do.

This is the objective, code-independent way to grade an AI-written test file, and it's
also the natural target for a follow-up prompt: instead of "add more tests," you can say
"here are the mutants that survived — write a test that kills each one." That's a much
more precise instruction than most human reviewers would think to give, and it's exactly
what you'll implement, in miniature, in the second exercise.

One honest caveat worth knowing before you rely on a mutation score: not every mutant is
killable. A mutation that produces code *semantically identical* to the original for
every possible input — an **equivalent mutant** — can never be killed by any test, no
matter how thorough. Stryker's own docs describe this as a known, unsolved limitation of
the technique, not a suite quality problem. A mutation score of 92% on a codebase with a
few equivalent mutants baked in can be a perfect score in practice.

### Characterization tests before a refactor

Before an agent (or you) restructures a chunk of code with unclear or undocumented
behavior, the safe move is to write **characterization tests** first: tests that record
what the code *currently* does, bugs included, with no judgment about whether that's
correct. They're not a spec — they're a tripwire. Once they're green, the refactor's job
is to keep them green while changing the internals. If a characterization test breaks,
you find out immediately whether that's an intended behavior change or a regression,
instead of finding out from a support ticket.

### Codemods and compiler-friendly refactors

Large mechanical refactors are exactly where AI assistance is strongest, because the
work is genuinely mechanical: a codemod. The `react-codemod` and `codemod.com` tool
families ship transforms for real React 19 migration pain points — replacing
`ReactDOM.render` with `createRoot`, dropping `propTypes` in favor of TypeScript, and
`types-react-codemod` for the type-only fallout of the split between `@types/react` and
React 19's own bundled types. An agent can run these, but the check is the same either
way: typecheck clean, tests green, and a diff small enough that a human can actually read
it — not "the codemod says it's done."

React Compiler (covered in lesson 14) adds a different kind of refactor target:
"compiler-friendly" changes, meaning removing manual `useMemo`/`useCallback`/`React.memo`
that the compiler now inserts automatically, and fixing any Rules-of-React violations the
compiler's linter flags before it will safely apply. react.dev frames this explicitly as
an automated optimization, not a correctness tool — it changes *when* work happens, not
*what* the component computes, which is exactly the property a characterization test
suite is positioned to confirm.

For any refactor above a few files, the same checks ladder applies regardless of who
proposed the diff: typecheck, tests, lint, a visual regression pass if the change touches
rendered output, and a bundle-size check if it touches what ships. Lesson 93's feature
flags are the mechanism for shipping a risky one incrementally instead of atomically. The
exercise after this one builds a small planner that applies exactly this ladder as a set
of rules.

### Accessibility automation's real ceiling

axe-core (deque.com/axe), the engine behind `vitest-axe`, `jest-axe`, and Lighthouse's
accessibility audit, is excellent at *structural* rules: missing alt text, invalid ARIA
attribute values, insufficient color contrast, unlabeled form fields, duplicate IDs.
Deque's own materials are explicit that automated testing catches a minority of WCAG
success criteria — commonly cited around half, since so much of the spec is about
*behavior* (does arrow-key navigation move focus correctly inside a listbox, does a live
region announce a status change, is the reading order sensible) rather than structure.
That's not a flaw in axe; it's a description of what's mechanically checkable at all
without a human or a screen reader in the loop. You built a miniature of exactly this
kind of structural rule engine in lesson 60.

AI fits into the gap axe leaves, as a drafting tool, not a verdict: drafting alt text for
an image (a human should still confirm it describes the *right* thing, not just *a*
thing), suggesting an ARIA attribute for a custom widget, or writing a first pass at a
keyboard interaction handler. The rule "no ARIA is better than bad ARIA" (from the W3C's
ARIA Authoring Practices Guide) applies just as much to AI-suggested ARIA as to
hand-written ARIA — an incorrect `role` or a redundant `aria-label` on a native element
can make a page *less* accessible than adding nothing. Screen reader testing — actually
tabbing through with VoiceOver or NVDA, in both browse and focus mode — stays a manual
step no automated tool including an LLM currently replaces.

One place automation is genuinely extending its reach: agentic browser audits, where an
agent drives a real page with Playwright and runs axe against every route it finds,
turning a single manual audit into something closer to continuous coverage. That still
inherits axe's ceiling — it finds more structural violations, faster, not more behavioral
ones.
