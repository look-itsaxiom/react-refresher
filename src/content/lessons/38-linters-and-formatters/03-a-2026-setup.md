Picking a linting stack in September 2026 means picking one of three shapes, then wiring
it into editors, hooks, and CI so it catches problems before a human has to.

## Three stacks, and when each wins

**Biome-only.** One Rust binary, one config file (`biome.json`), formatter and linter
together, sub-second on most repos, zero plugin ecosystem to manage. Its `noFloatingPromises`-
style rules now work via Biome's own type-inference engine without a `tsconfig.json` or
a `typescript` install at all — a deliberate trade-off: it infers enough to catch real
bugs without claiming to be a type checker. Right choice for most new projects that don't
need a long tail of framework-specific rules.

**oxlint + ESLint.** oxlint runs the syntactic rules (and, as of its `tsgolint`
integration reaching a stable v7 in 2026, the type-aware ones too, built on
`typescript-go`) at Rust speed, and a thin ESLint layer picks up only the plugins oxlint
doesn't replicate yet — `eslint-plugin-jsx-a11y` is the common one, since oxlint's
accessibility coverage is still catching up. Right choice when you want oxlint's speed
but have a plugin your team can't drop.

**ESLint flat config, full typescript-eslint.** `eslint.config.js` (or, since ESLint
9.9, an experimental `eslint.config.ts` — native without a loader on Node ≥22.13 via
`--experimental-strip-types`, or via `jiti` otherwise) exporting an array of config
objects, each scoping `files`, `languageOptions`, `plugins`, and `rules`. This is still
the only path to the full third-party plugin ecosystem, and the only one with
`eslint-plugin-react-hooks` v7's compiler-derived rules
(`purity`, `immutability`, `set-state-in-render`, `refs`, `static-components` — see the
React Compiler lesson) built in. Right choice when a plugin only exists for ESLint, or
when a team already has years of shared config invested here.

## The TypeScript 7 wrinkle

TypeScript 7.0 (the Go-native compiler, GA July 8, 2026) shipped **without** a public
programmatic compiler API — no `ts.createProgram`, no `ts.factory`. `typescript-eslint`'s
type-aware rules are built entirely on that API, so `typescript-eslint@8`'s peer range
caps at `typescript < 6.1`, and installing `typescript@7` alongside it fails outright.
TypeScript 7.1's iteration plan (published July 31, 2026) targets that API returning in a
beta around October 2026, after which typescript-eslint is expected to ship support. Until
then, teams running TS7 for `tsc` have two workarounds: pin `typescript@6.x` (or
Microsoft's `@typescript/typescript6` compatibility shim) just for ESLint's type-aware
pass, or skip typescript-eslint's typed rules entirely and get type-aware linting through
oxlint's `tsgolint` instead — it builds its own `ts.Program` directly on `typescript-go`
and was never depending on the missing API in the first place. For a project already on
TS 7 like this one, that second path — oxlint (with `tsgolint` for the handful of typed
rules worth the cost) plus Biome or oxfmt for formatting — sidesteps the gap completely
rather than waiting on it.

## Wiring it in without fighting it

- **Editor integration.** Format-on-save via the editor's LSP extension (Biome's or
  oxlint's, or ESLint's `eslint.config.js` + a formatter extension), not a separate "run
  prettier" step. If format-on-save and CI disagree about the config, that mismatch is
  the single most common source of "why did this PR touch 400 unrelated lines."
- **CI is the actual gate.** Editor integration is a courtesy; nothing prevents a
  contributor from disabling it. A pipeline step that runs the linter and formatter in
  `--check`/CI mode (never `--write`) and fails the build is what makes the rule
  enforceable rather than advisory.
- **Pre-commit vs pre-push.** `lint-staged` (paired with Husky, still the most common
  combination by download count) or `lefthook` (single YAML file, no Node dependency,
  runs hooks in parallel — meaningfully faster on large repos) run the fast, syntactic
  checks against staged files before a commit lands. Type-aware rules and full-repo
  passes belong at pre-push or in CI instead — running a `tsc`-backed rule set on every
  commit is the fastest way to get a team disabling the hook.
- **Incremental adoption.** Dropping a linter into a legacy codebase with thousands of
  existing violations either means fixing everything at once (rarely realistic) or using
  a **baseline**: run the linter once, snapshot every current violation
  (`eslint --suppress-all` and comparable Biome/oxlint "suppression file" flows), and
  configure the tool to fail only on *new* violations. The debt gets tracked and paid
  down deliberately instead of blocking every unrelated PR.

## The rules worth having, specifically

- `react-hooks/rules-of-hooks` — the exact shape this lesson's exercise implements:
  no hook call inside a condition, loop, or after an early return.
- `react-hooks/exhaustive-deps` — still relevant for `useEffect`, `useMemo`, and
  `useCallback` dependency arrays in code the React Compiler doesn't touch or can't
  prove safe; the compiler-era rules from `eslint-plugin-react-hooks` v7
  (`set-state-in-effect` and friends) catch a different, newer class of bug and don't
  replace this one.
- `jsx-a11y/*` — accessibility mistakes (missing `alt`, a `<div onClick>` instead of a
  `<button>`, an unlabeled form control) that no type checker will ever catch, because
  they're valid TypeScript and valid JSX.
- `no-floating-promises` — an `async` call whose result is neither `await`ed nor
  otherwise handled; the single highest-value type-aware rule for React code, since a
  dropped promise inside an event handler fails silently.
