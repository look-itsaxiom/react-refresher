## CSRF in 2026: mostly dead, still dangerous

Cross-site request forgery is the attack that exploits the gap from lesson 62: the
same-origin policy stops a malicious page from *reading* another origin's response, but
it never stopped that page from *sending* a request with your ambient cookies attached.
A form on `evil.example` that posts to `https://bank.example/transfer` still carries your
`bank.example` session cookie, because cookies are sent by target, not gated by who
initiated the request. For twenty years that gap was wide open. Today, `SameSite`
defaults close most of it — but "most" is doing real work in that sentence, and knowing
exactly which slice survives is what separates a team that ships one mitigation and moves
on from one that gets popped by the slice they didn't cover.

### What SameSite-by-default actually changed

Since Chrome 84 (2020), followed by Firefox and Safari, a cookie set with no explicit
`SameSite` attribute is treated as `SameSite=Lax`. The three values, precisely:

- **`Strict`** — never sent on a cross-site request, full stop, including a user clicking
  a link into your app from email or another site. (That last part is why `Strict` is
  rare for session cookies: it breaks "click a link, land logged in.")
- **`Lax`** — sent on a cross-site **top-level navigation** with a "safe" method (a
  clicked link, `window.location` redirect, a GET form submission), but withheld on
  cross-site **subresource** requests: `<img>`, `<script>`, `fetch`/`XHR`, an iframe load.
  This is the default now, and it kills the classic "hidden `<img src>` triggers a
  state-changing GET" and "hidden iframe auto-submits a POST via `fetch`" attacks outright.
- **`None`** — sent on every request regardless of site, and as of 2020 this requires
  `Secure` in the same `Set-Cookie` — a browser rejects `SameSite=None` without `Secure`
  entirely. You reach for `None` deliberately, for cookies that must work when your app is
  embedded or called cross-site on purpose (a payment widget, an SSO iframe).

"Site" here is **schemeful same-site**: the registrable domain plus scheme, so
`https://app.example.com` and `http://app.example.com` count as different sites even
though they share a domain, and `checkout.example.com` and `app.example.com` are the
*same* site (same eTLD+1) even though they're different origins. `SameSite` compares
sites, not origins — which is also why a subdomain takeover (an attacker getting control
of some forgotten `old-app.example.com`) is a same-site request as far as cookies are
concerned, and sails past every `SameSite` setting.

### What survives Lax-by-default

Four things, concretely:

1. **The Lax+POST exception.** Chrome ships a temporary, intentionally time-boxed
   mitigation: a cookie with no explicit `SameSite` (Lax by default) is *still* sent on a
   cross-site top-level **POST** navigation — a plain HTML form, not `fetch` — if the
   cookie was set within roughly the last **two minutes**. This exists so sites that
   depend on cross-site POST logins (some SSO and payment flows) don't break overnight;
   it also means a freshly-authenticated session has a short window where a classic form-
   based CSRF POST still works, even with no `SameSite` attribute set at all.
2. **State-changing GET.** A GET request that mutates state (`/unsubscribe?id=42`,
   `/delete?id=1`) is reachable via a plain link or a GET form — both are top-level
   navigations, both are allowed under `Lax`. This was always bad HTTP semantics (GET is
   supposed to be safe/idempotent); `SameSite` doesn't rescue you from having ignored that.
3. **`SameSite=None` cookies, by design.** Anything that legitimately needs cross-site
   delivery opts back into full exposure. If that cookie also authenticates a
   state-changing endpoint, it needs its own defense layer — `SameSite` isn't providing
   one anymore.
4. **Login CSRF.** Forging a request that logs the *victim* into the *attacker's*
   account (not stealing the victim's session, but planting the attacker's) is often
   overlooked because "there's no sensitive action here yet" — until the victim later
   enters real data (a saved card, a search history) into a session the attacker controls.

### Defense in layers

`SameSite=Lax` (or `Strict` where UX allows) is the floor, not the whole defense:

- **Fetch Metadata headers** — `Sec-Fetch-Site` (`same-origin`, `same-site`,
  `cross-site`, `none`), `Sec-Fetch-Mode`, `Sec-Fetch-Dest` — are sent by the browser on
  every request, unspoofable by an attacker page, and let a server reject a
  state-changing request whose `Sec-Fetch-Site` is `cross-site`. This is cheap,
  requires no per-request token, and closes the Lax+POST and state-changing-GET gaps in
  one rule.
- **`Origin` (and, as fallback, `Referer`) header verification** — compare the request's
  `Origin` to the server's own host on any state-changing request; reject a mismatch.
  Older than Fetch Metadata, still valid, and it's exactly what frameworks reach for.
- **Synchronizer tokens** — a per-session (or per-form) random value embedded in the
  page and required back on submit; the attacker's page can't read it because reading it
  would require crossing the same-origin policy it's trying to exploit around.
- **Double-submit cookies (signed)** — a token set as a *readable* cookie and also
  required as a request parameter or header; the server checks they match. "Signed"
  matters: an attacker who can plant their own cookie on your origin (rare, but possible
  via a subdomain) can otherwise supply a matching pair. A signed variant (an HMAC over
  the token plus a server secret) blocks that.
- **Custom headers.** Requiring a custom header (`X-Requested-With`, or any
  application-specific one) on state-changing requests forces a CORS preflight for any
  cross-origin `fetch`, and a plain HTML form can't set custom headers at all — so this
  incidentally blocks the classic vectors, though it's a side effect of CORS, not a
  purpose-built CSRF defense.

### How frameworks handle it now

Next.js Server Actions check the request's `Origin` header against the server's `Host`
on every action invocation and reject a mismatch, so a plain cross-site form post to a
Server Action's endpoint is rejected before your code runs — you get this for free, not
as something you opt into. Remix/React Router's data APIs (`action` functions) don't
enforce this automatically; the framework's own guidance is to add `Origin` or Fetch
Metadata checks yourself if an action performs a sensitive mutation and doesn't already
require a matching CSRF token. The pattern across frameworks in 2026 is the same
direction of travel: push the origin check into the framework layer so an individual
route author doesn't have to remember it, the same way CORS moved from "manual header"
to "framework config" over the last decade.

### Bearer tokens change the threat, not the effort

An SPA that authenticates with a bearer token attached manually (an `Authorization:
Bearer <token>` header, from `localStorage` or memory, not an ambient cookie) is not
vulnerable to classic CSRF: a forged cross-site request has no way to attach a header
the victim's browser doesn't automatically send. That is a real property, not a myth —
but it isn't "solved," it's "moved." The token now has to live somewhere JavaScript can
read it to attach it, which means anyone who can run script in your page (XSS) can read
and exfiltrate it just as completely as a CSRF attack could act on a cookie. Lesson 63
covered why that trade concentrates all your risk into one control (script injection);
this is the other half of why the sessions-vs-tokens decision (lesson 69) is a security
decision, not just an architecture one.
